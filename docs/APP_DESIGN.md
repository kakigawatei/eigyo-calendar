# 柿川亭／アブララボ「月間 営業カレンダー」作成ツール 設計書

対象店舗: 柿川亭（本店）／アブララボ（油ラボ）の2店舗（将来グループ6店舗に拡張の可能性あり）
利用者: masa（1人運用が基本。将来は社員が編集する可能性もあるが本書では単一利用者を前提に設計）
最終形: 「今月のカレンダーを開く→曜日ごとの基本パターンを確認→変更が出た日だけ直す→印刷 or 画像保存→店頭に貼る」を数分で終わらせる。**紙に手書きで修正する運用をゼロにする**のがゴール。
実装方針: 段階的。Phase1＝**紙の代わりに画面で作って印刷できる最小版**から着手し、Phase2で「曜日パターンの一括適用」「月の引き継ぎ」「PNG書き出し」、Phase3で「祝日自動表示」「SNS比率書き出し」を積む。
配信方式: インストール不要のPWA（GitHub Pages＋クライアントJS、ビルドなし）。データはlocalStorage（ブラウザ内保存）。将来、複数端末で編集したい／社員と共有したい要望が出た場合のみFirestore移行を検討する（`shime-app`と同じFirebaseプロジェクト`kakigawatei-franchise`を流用可能）。

## 0. 前提として読んだ資料・観察したこと

`docs/reference/current_calendar_abura_202607.jpg` ＝アブララボの2026年7月の実物カレンダー（お店のガラス面にラミネートして掲示、印刷後に手書き修正が加筆されたもの）を読み込んで観察した。

### レイアウト
- 縦長1ページ（A4想定）を左右2ブロックに分割。
  - **左ブロック（狭い・情報エリア）**：上から「07」（大きな2桁数字）／「July」／「2026」／店ロゴ「アブララボ ながおか」＋英字タグライン3行（EAT IN & TAKE OUT & DELIVERY / NOODLE.ANY FOODS / FROM KAKIGAWATEI）＋丼アイコン／注意書き2文（「不定期に休業することがあります。」「営業日の変更がありましたらgoogleMAP・instagramなどでお伝えします。」）。
  - **右ブロック（広い・カレンダー本体）**：月曜始まりの7列グリッド（月火水木金土日）。月初が水曜なので1行目の月・火は空白セル。最終行（27〜31）の後ろの土・日は空白のまま埋めない＝「その月に存在する日付ぶんだけ描く」方式（月末を7の倍数に合わせて空セルで埋め立てない）。
- 土曜列だけ薄い水色の背景（曜日の意味ではなく単なるアクセント。休業日でも土曜なら水色のまま）。

### 各日セルの表示パターン（＝状態の種類）
実物から4種類の状態が確認できた。
1. **営業**：時間帯を2段で表示。「11:00〜14:00」＋「17:00〜20:00」（昼営業／夜営業の2部制、時刻はいずれの営業日も同じ値で固定）。
2. **定休日**（オレンジ文字）：あらかじめ決まっている曜日の休み。
3. **休業**（オレンジ文字）：不定期の休み（臨時休業）。
4. **夕方休業**（オレンジ文字、7/27は印刷時点でこの表記＝あらかじめ分かっていた夜だけの休み）。

日付数字は各セルの左上に小さく表示。祝日は日付の右に名称を添える（例：「20 海の日」、名称もオレンジ系の色）。

### 手書き修正（＝なくしたい運用）
2箇所で「印刷後の手直し」が確認できる。
- 7/10（金）：印刷時は通常営業（11:00〜14:00／17:00〜20:00）だったが、17:00〜20:00を二重線で消し、下に手書きで「夕方休業」を追記。
- 7/22（水）：同様に17:00〜20:00を消して「夕方休業」を手書き追記。
- 7/24（金）：11:00〜14:00と17:00〜20:00の両方を二重線で消し、「休業」を手書き追記（全休扱いへの変更）。

→ この「時間を消して状態ラベルを手書きする」作業が、まさに本ツールで**画面上のタップ操作に置き換える**対象。

### 既定の曜日パターンが実在する（重要な発見）
実物の「定休日」がついた曜日を全行で追うと、**火曜・木曜・日曜は毎週必ず「定休日」**（7列中どの週も一致）で、月・水・金・土は基本営業（例外的に休業/夕方休業になる日がある）という、明確な**週次の既定パターン**が運用されている。これは今回の設計要求（2-c：曜日の既定パターンを先に設定→月に一括適用）が実際の運用実態と一致していることの裏付けであり、Phase2の「曜日パターン一括適用」機能の価値を裏付ける観察事実として記録しておく（曜日ごとの正確な既定はmasaに確認する＝質問リスト参照。店舗によって異なる可能性もある）。

### 柿川亭側の体裁は不明
今回渡された実物はアブララボのみ。柿川亭を同じ仕組みで運用するかどうか、ロゴ・タグライン・注意書き文言・営業時間の型が同じか別かは未確認（質問リストに記載）。

## 1. アプリ全体像とコンセプト

### コンセプト
**「今月のカレンダーを開く→違うところだけ直す→出す」**。
今の運用は「毎月まっさらな紙にゼロから曜日パターンを手作業で書き起こし、印刷し、その後の変更をペンで消して書き直す」という**作り直しコストが高い**フローになっている。これを、①既定の曜日パターンは月をまたいで引き継がれる、②個別の変更はその日のセルをタップして状態を選ぶだけ、③出力（印刷・画像）はワンタップ、という形に置き換える。

### 基本フロー
```
① 店舗を選ぶ（柿川亭 / アブララボ）
        ↓
② 対象の月を選ぶ（前月から曜日パターンを引き継ぎ）   … Phase2〜
        ↓
③ 曜日の既定パターンを確認・調整                    … Phase2〜
   （例：月・水・金・土＝営業11-14/17-20、火・木・日＝定休日）
        ↓
④ その月だけの例外を個別の日に上書き
   （休業／夕方休業／時間変更／祝日名の付与）
        ↓
⑤ プレビューを確認
        ↓
⑥ 印刷（A4）／画像として保存（PNG）
        ↓
⑦ 変更が出たら④に戻って直す→⑤⑥をやり直すだけ（作り直しではなく、直して出すだけ）
```

### 画面には「今月ここまで作った」状態が見える
編集中の月は自動保存（localStorage）され、次に開いたときは続きから編集できる。印刷・保存のたびに「最終更新: 7/31 21:10」のような表示を出し、「今貼ってあるカレンダーは最新かどうか」をmasa自身が判断しやすくする。

## 2. データモデル

Firestoreは使わず、**localStorageのみ**（Phase1〜3共通。将来複数端末共有が必要になった場合のみFirestore化を検討＝§6参照）。キー設計は将来Firestoreに移すときにコレクション名へそのまま転用できる形にしておく。

### `storeProfile_{store}` （店舗プロフィール。頻繁には変えない）
```json
{
  "storeId": "abura",
  "displayName": "アブララボ ながおか",
  "tagline": ["EAT IN & TAKE OUT & DELIVERY", "NOODLE.ANY FOODS", "FROM KAKIGAWATEI"],
  "logoIcon": "bowl",
  "noticeLines": [
    "不定期に休業することがあります。",
    "営業日の変更がありましたらgoogleMAP・instagramなどでお伝えします。"
  ],
  "satColor": "#cfe3ef",
  "closedColor": "#e8946a",
  "defaultHoursPresets": [
    { "id": "lunch_dinner", "label": "2部営業", "slots": [["11:00","14:00"], ["17:00","20:00"]] },
    { "id": "lunch_only",   "label": "昼のみ",   "slots": [["11:00","14:00"]] },
    { "id": "dinner_only",  "label": "夜のみ",   "slots": [["17:00","20:00"]] }
  ]
}
```

### `weekPattern_{store}` （曜日の既定パターン。Phase2で編集画面を用意。月を新規作成する際にこれをコピーして初期値にする）
```json
{
  "mon": { "status": "open", "hoursPreset": "lunch_dinner" },
  "tue": { "status": "regular_closed" },
  "wed": { "status": "open", "hoursPreset": "lunch_dinner" },
  "thu": { "status": "regular_closed" },
  "fri": { "status": "open", "hoursPreset": "lunch_dinner" },
  "sat": { "status": "open", "hoursPreset": "lunch_dinner" },
  "sun": { "status": "regular_closed" }
}
```

### `calendar_{store}_{YYYYMM}` （その月の実データ。曜日パターン＋日ごとの上書き）
```json
{
  "store": "abura",
  "yyyymm": "202607",
  "weekPatternSnapshot": { "...": "月作成時点のweekPatternのコピー（後からweekPatternを変えてもこの月には影響しない）" },
  "dayOverrides": {
    "2026-07-10": { "status": "evening_closed", "note": "" },
    "2026-07-22": { "status": "evening_closed" },
    "2026-07-24": { "status": "closed" },
    "2026-07-20": { "holidayName": "海の日" }
  },
  "updatedAt": "2026-07-31T21:10:00+09:00"
}
```
**「その日の実際の表示」＝ `dayOverrides[date]` があればそれを優先、なければ `weekPatternSnapshot[曜日]` を使う（マージ）**、という1本のルールで解決する（状態・時間・祝日名それぞれ個別にオーバーライド可＝時間だけ変えて状態はopenのまま、祝日名だけ付けて状態は変えない、といった部分上書きにも対応）。

状態（`status`）の種類：
| 値 | 表示 | 色 |
|---|---|---|
| `open` | 時間帯を表示（hoursPresetまたは個別slots） | 黒文字 |
| `regular_closed` | 定休日 | オレンジ |
| `closed` | 休業 | オレンジ |
| `evening_closed` | 夕方休業（＝昼のみ営業） | オレンジ |
| `custom` | 自由入力テキスト（例：「臨時営業」「貸切」等） | オレンジ |

### `holidaysJp`（Phase3・内蔵祝日テーブル。§5参照）
アプリに静的データとして同梱。ユーザー編集はしない（自動表示のみ。個別に変えたい場合は `dayOverrides` の `holidayName` で上書き）。

## 3. 画面構成

### 3-1. 起動画面（店舗・月選択）
```
┌───────────────────────────────┐
│   月間 営業カレンダー 作成ツール          │
│                                  │
│   店舗： [柿川亭] [アブララボ●]          │
│   月：   [◀ 2026年6月] [2026年7月●] [8月▶]│
│                                  │
│        [ この月を編集する → ]         │
│                                  │
│  最近編集した月：                       │
│  ・アブララボ 2026年7月（最終更新7/31）    │
│  ・アブララボ 2026年6月                 │
└───────────────────────────────┘
```
店舗はタブで即切替。月は左右矢印＋直近編集履歴から選べる。新しい月を開くと、直前の月の`weekPatternSnapshot`を初期値としてコピーする（Phase2）。Phase1では初期値は`weekPattern_{store}`（曜日パターン編集画面ができるまでの暫定・§7参照）。

### 3-2. 曜日パターン編集（Phase2）
```
┌───────────────────────────────┐
│ アブララボ - 曜日の既定パターン           │
├───────────────────────────────┤
│ 月  [営業●] [定休日] [休業]              │
│     時間: [2部営業(11-14/17-20)▾]      │
│ 火  [営業] [定休日●] [休業]              │
│ 水  [営業●] ...                       │
│ … （7曜日ぶん）                        │
├───────────────────────────────┤
│ [ この設定を今月に適用 ]                  │
│ ※すでに個別修正した日は上書きされません      │
└───────────────────────────────┘
```
ここで決めた既定は「型」として保存され、月を新規作成する際のコピー元になる。「今月に適用」ボタンは、既に`dayOverrides`が入っている日をつぶさないよう、**個別上書き済みの日は対象外**にする（誤操作で手直しが消えるのを防ぐ）。

## 4. カレンダー描画・出力の方式（設計の要）

### 4-1. 描画の共通ソース
編集画面のプレビューも、印刷も、PNG書き出しも、**同じデータ（§2のマージ結果）から3通りの見た目を作る**。二重管理を避けるため、「1日分のセルの中身（日付・状態ラベル・時間・祝日名・色）」を作る関数を1つ用意し、HTML描画／印刷用HTML／Canvas描画のいずれもそこを通す。

### 4-2. 印刷（第一の主力＝実物の掲示品質をそのまま再現）
- HTML＋CSSでレイアウトを組み、`@media print` で印刷用スタイル（A4サイズ、余白、実物と同じ配色・罫線）を定義し、ブラウザ標準の印刷機能（`window.print()`）で出す。
- 利点：**文字も罫線もベクター品質で最も綺麗**、iPhone Safari・PC Chromeどちらでも標準機能だけで完結、ライブラリ依存ゼロ。「印刷→PDFとして保存」もブラウザ標準機能でそのまま使える（印刷が難しい場所ではPDF保存でも代用可）。
- 用紙サイズ・向き（A4縦か横か）は実物を踏襲するならA4縦（実物の写真は縦長1ページに左狭・右広の2ブロックを収めるレイアウト）。CSSの`@page { size: A4 portrait; margin: 10mm; }`で固定し、印刷ダイアログの用紙設定に依存しすぎないようにする。
- masaへの確認：実物は現在どの向き・どのプリンタ／サイズで刷っているか（質問リスト参照）。

### 4-3. 画像（PNG）保存（Instagram・GoogleMAP掲載用、Phase2〜）
- **html2canvas等のスクリーンショット系ライブラリは使わない**（フォントレンダリングのブレ・外部ライブラリ依存を避けるため）。
- 代わりに、**Canvas 2D APIで直接描画**する専用の描画関数（`renderCalendarToCanvas(data, sizePreset)`）を実装する。§2のマージ済みデータを受け取り、`fillRect`/`fillText`等で罫線・文字・色を直接描く。HTML版と見た目を合わせるため、フォント・色・余白の定数（テーマ定義）をHTML用CSSとCanvas描画側で共通の1つのJS定数オブジェクトから参照する（値のズレを防ぐ）。
- 書き出しは`canvas.toBlob()` → `URL.createObjectURL` → ダウンロードリンク、またはモバイルでは「画像を長押しして保存」に対応できるよう`<img>`化して表示する導線も用意する（iPhone Safariのダウンロード挙動を考慮）。
- サイズプリセット：掲示画像そのまま比率（Phase2）に加えて、Phase3でInstagram正方形（1080×1080）・ストーリー（1080×1920）比率のレイアウトを別途用意する（左の情報ブロックと右のグリッドの配置比率を比率ごとに調整するバリエーションを持たせる）。

## 5. 祝日の扱い

オフラインの店頭掲示端末や、外部通信を前提にしたくない運用を考慮し、**内蔵の静的テーブル方式**を基本とする。
- `holidays_jp.js` のような静的JSONを同梱し、`"2026-07-20": "海の日"` のように日付→祝日名の対応表を持つ。数年分（例：当年＋前後2年）をあらかじめ用意し、年1回程度、内閣府発表の最新の祝日情報に合わせて手動更新する（振替休日のルールも含めて年によって変動するため、計算式で毎回自動算出するより**確定値の一覧を持つ方が安全確実**）。
- 対象日を開くと自動的に祝日名候補が表示され（例：7/20を選ぶと「海の日」が自動でプレースホルダ表示）、そのまま採用するか、`dayOverrides`の`holidayName`で書き換えるかを選べる。
- 内蔵テーブルにない日・独自にラベルを付けたい日（例：店の記念日、地域のお祭り）は普通に`holidayName`欄へ手入力すればよく、自動テーブルと手動入力は競合しない設計とする。

## 6. 技術構成

- **配信**：GitHub Pages（新規リポジトリ、例 `kakigawatei/eigyo-calendar`。現在のローカル`C:\Users\masat\Desktop\eigyo-calendar`はgit初期化済み・リモート未設定＝要masa作業）。
- **フロントエンド**：ビルドレスの静的HTML/CSS/バニラJS。`nagaoka-walk`・`shime-app`と同じ流儀（フレームワーク・バンドラなし、`index.html`＋数本のJSファイル構成）。
- **PWA化**：`manifest.webmanifest`＋`sw.js`（アプリシェルのキャッシュファースト）。「ホーム画面に追加」でアイコンから起動できるようにする（他アプリと統一）。
- **データ層**：Phase1〜3は`localStorage`のみ（サーバー・通信一切なし＝オフラインの掲示端末でも完結）。将来、複数端末・複数人で同じ月を編集したい要望が出た場合のみ、`shime-app`と同じFirestore REST直叩きパターン（匿名認証＋`kakigawatei-franchise`プロジェクト）への移行を検討する（本書では方針のみ明記し、着手はしない）。
- **印刷**：ブラウザ標準の`window.print()`＋`@media print`（§4-2）。
- **画像書き出し**：Canvas 2D APIによる自前描画（§4-3、外部ライブラリ非依存）。
- **祝日データ**：静的JSON同梱、年1回手動更新（§5）。
- **ファイル構成イメージ**：
  ```
  index.html          … 起動〜店舗/月選択〜編集〜出力プレビューまでの単一ページアプリ
  ```

## 7. 段階的ロードマップ

### Phase1：紙をやめて画面で作れる最小版
**スコープ**：1店舗（どちらか先に使う店をmasaと決める）、当月のみ編集可能。曜日パターン編集画面は作らず、新規月を開いた際は簡易な既定値（例：全曜日「営業・2部営業」で初期化、または前回月の内容をそのまま複製）から開始し、あとは1日ずつタップして状態（営業／定休日／休業／夕方休業／カスタム）・時間・祝日名を設定する。出力は印刷（A4・`@media print`）のみ。localStorageへの自動保存はここから実装（次に開いた時に続きから編集できる）。
**完了条件**：masaが「今月ぶん、紙に手書き修正を一切せずに」このツールだけでカレンダーを作って印刷し、店頭に貼れる状態が1か月以上続く。

### Phase2：曜日パターンの一括適用・月の引き継ぎ・PNG書き出し
**スコープ**：`weekPattern_{store}`編集画面（§3-2）を追加。新規月作成時に前月の`weekPatternSnapshot`を自動引き継ぎ。個別上書き済みの日を保護する「今月に適用」ロジックを実装。Canvas描画によるPNG書き出し（§4-3）を追加。2店舗目（柿川亭）にも対応（店舗プロフィールとタグライン・注意書きを追加登録）。
**完了条件**：月初に「先月の型をベースに、変わった曜日だけ直す」だけで数分以内に新しい月を用意できる。SNS投稿用にPNGをそのまま使える。

### Phase3：祝日自動表示・SNS比率書き出し
**スコープ**：内蔵祝日テーブル（§5）を実装し、日付選択時に祝日名を自動提案。PNG書き出しにInstagram正方形／ストーリー比率のレイアウトバリエーションを追加。
**完了条件**：祝日名の入力漏れが減り、店頭掲示用とSNS用を同じ元データから使い分けられる。

## 8. masaに確認すべきオープンな質問リスト（実装前に必須）

### 体裁・ブランドまわり
1. 柿川亭側も同じ仕組みでカレンダーを作りたいか。作る場合、柿川亭のロゴ画像・タグライン・注意書き文言・営業時間の型（アブララボと同じ2部制か別か）を教えてほしい（今回はアブララボの実物しか受け取っていないため）。
2. 実物の配色（オレンジ・水色）や罫線の色は、正確な色（お店のブランドカラーの指定があれば）を合わせたいか、今回の写真から近似で拾ってよいか。
3. 「不定期に休業することがあります。」等の注意書き文言は、店舗ごとに固定でよいか、月によって変えることがあるか。

### 運用まわり
4. **「夕方休業」の正確な定義**：昼(11:00〜14:00)のみ営業して夜(17:00〜20:00)を休むという理解でよいか。逆に「昼だけ休んで夜だけ営業する」パターンもあり得るか（その場合は状態をもう1種類増やす）。
5. 曜日の既定パターン（今回の観察では火・木・日＝定休日、月・水・金・土＝営業）は、この理解で合っているか。店舗（柿川亭）でも同じパターンか、別か。
6. 現在の印刷は用紙サイズ・向き（A4縦／横）、プリンタ環境（お店のプリンタ／コンビニ印刷／PDF経由）はどうなっているか。掲示のラミネート加工も込みで運用が変わる場合があれば教えてほしい。
7. PNG画像での書き出しは実際に使う予定があるか（Instagram・GoogleMAPへの掲載用）。あるなら、掲示物そのままの比率でよいか、正方形などSNS向けの別レイアウトも要るか。
8. 祝日表示は自動（内蔵テーブル）でよいか、それとも今まで通り必要な時だけ手入力で十分か（内蔵テーブルにしても手入力での上書きは常に可能）。
9. 将来、締めアプリ（shime-app）や会計側の「臨時休業」情報とこのカレンダーを連携させたい意向はあるか（例：締めアプリ側で「明日休業」を記録したらこちらにも自動反映、等）。今は不要でも構わないが、方向性だけ把握しておきたい。
10. 利用者はmasaのみか、社員も編集する可能性があるか（複数人・複数端末での編集が必要になった場合のみFirestore化を検討するため）。
